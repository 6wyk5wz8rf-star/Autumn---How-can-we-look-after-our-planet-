# Build 4 handover

## Released Build 3 baseline

Build 3 releases **Living Things Observatory** as the third open destination in **How Can We Look After Our Planet?**. Build 4 must extend this product in place. It must not create a separate Climate Laboratory application, replace stable Atlas/Number/science engines, or change any released ID or four-digit code.

The released child destinations are:

- Planet Atlas — `#/atlas`
- Number Expedition — `#/numbers`
- Living Things Observatory — `#/living-things`

Living Things Observatory contains six connected regions, 18 open scientific tools, 16 guided Key Activities, five Collection keys, and one Environment key. The product manifest contains 72 records: 52 Activities, 14 Collections, three Environments, one Whole World key, and two separated adult entrances. The production Teacher Key Room projects 70 active child pathway records and permanently reserves `8584`.

## Contracts Build 4 must preserve

Preserve without reassignment or destructive migration:

- every Build 1–3 key code, stable activity ID, destination ID, route, wildcard, and grant meaning
- local profiles, scaffold/accessibility settings, active-profile state, and profile separation
- Atlas map state, place IDs, snapshots, place links, Planet Question history, and saved geography work
- Number Expedition values, representation state, generator seeds, mathematical artefacts, and formal-calculation conventions
- Living Things organism/habitat IDs, source/rights records, feature vocabulary, classification questions and trees, generator seeds, survey provenance, evidence labels, and scientific artefacts
- version history, duplication, backup/import, quarantine, teacher favourites, Board View preferences, and print contracts
- session-only `8584` behaviour and hidden legacy compatibility entrance `4829`
- `7046` as the future-aware Whole World wildcard
- database schema version 3 unless a genuinely new store or index makes an additive migration necessary

Do not clear IndexedDB, repurpose a field, silently reinterpret an existing record, or make a wildcard finite.

## Climate Laboratory boundary

Build 4 may activate the existing `climate-laboratory` destination only when its open experience, guided pathways, local data, accessibility, print, persistence, teacher projection, validation, and offline assets are complete.

Climate Laboratory should distinguish:

- weather from climate
- one measurement from a long-term pattern
- temperature from change in temperature
- rainfall amount, frequency, and seasonality
- climate zone from biome, habitat, country, and exact species occurrence
- observed/source data from a generated learning scenario
- a plausible consequence from a confirmed effect
- broad global warming evidence from one local day or event

Do not activate a decorative climate slider or imply that one variable produces a scientifically complete biome.

## Reusable Build 3 science contracts

### Evidence language

Reuse the four stored labels:

- `evidenceStatement` — what a view, source, measurement, or model directly shows
- `knownStatement` — relevant established information
- `predictionStatement` — a possible result linked to the evidence
- `uncertaintyStatement` — information still needed

Climate records should preserve source, date/year, location, unit, method/aggregation where known, and a rounding note. Generated or fictional data must be visibly labelled and must never masquerade as a real climate statistic.

### Habitat and organism links

Reuse stable `habitatId` and Atlas place references. A climate record may describe a condition relevant to a habitat, but it must not assert that:

- a country is one habitat
- a climate zone contains the same habitats everywhere
- every species associated with a biome occurs at every mapped point
- a map location proves species presence
- all organisms respond to a change in the same way

Species-location links require their own researched occurrence evidence.

### Deterministic generation

Extend the functional seeded generator pattern. Every generated task should store generator version and seed, validate before display, and reproduce after reopening. Keep source data separate from generated teaching values.

### Shared My Work envelope

Register climate artefact types in `src/data/artefactTypes.js` and store semantic climate state inside the existing versioned envelope. Reopen the live model rather than a screenshot. Continue immutable revisions and independent duplication.

## Atlas and Number Expedition adapters

Climate Laboratory should link to Atlas through stable place IDs and matched map contexts. It should link to Number Expedition only where mathematics strengthens the climate evidence, for example:

- signed temperature values and movement through zero
- truthful scaled number lines
- comparison and difference
- rounding with a stated unit and purpose
- simple totals or averages only when curriculum scope and source metadata support them

Do not invent environmental statistics to create arithmetic practice.

## Central manifest and Teacher Key Room

Add climate Activity, Collection, and Environment records only to the central key manifest. Each active record needs a permanent non-obvious four-digit code, stable ID, route, curriculum tags, purpose, print information, outcome, suggested use, Board suitability, and approximate time.

The existing projection will then provide search, subject/environment/scale filters, display, copy, print, Quick Keys, and favourites. Do not maintain a second teacher list. `8584` and `4829` remain adult-only and never enter learner history or My Keys.

## Offline, performance, and assets

The build process injects every emitted application asset into the service worker. Keep climate datasets and graphics local, bounded, and source-dated. Prefer accessible HTML/SVG to canvas-only rendering, lazy-load the climate destination, and do not load all data resolutions at startup.

An offline release gate must cover an online installation followed by cold navigation to all three existing destinations and Climate Laboratory, guided keys, My Work, Teacher Key Room, profile switching, and print preparation.

## Build 4 acceptance gate

Before publishing Build 4:

1. Re-run every Build 1–3 test and verify every released code retains its exact meaning.
2. Import representative Build 1 and Build 2 backups and the exact Build 3 production schema without data loss.
3. Validate every sourced climate record, unit, year, location, licence/rights record, and rounding note.
4. Run large deterministic generator batches and reject invalid ranges, scales, units, and causal claims.
5. Manually review climate and environmental-change language for false certainty, fear, blame, and geographic stereotyping.
6. Test open exploration, all new keys, `8584`, Whole World wildcard expansion, My Work versions, Board View, print, profile separation, iPad portrait/landscape, enlarged text, keyboard/touch, reduced motion, and offline use.
7. Commit and push the verified tree to `main`, wait for CI and Pages, and repeat the key child/teacher journeys on the deployed origin.

## Known Build 3 limits

- Organism images are original diagrammatic SVGs, not photographs, measured anatomical plates, or scale evidence.
- Occurrence fields provide broad researched context; they are not live distribution, abundance, or conservation-status data.
- Habitat Builder and Change Laboratory are deliberately bounded reasoning models, not ecosystem or population simulations.
- The local Survey Builder does not identify organisms automatically, collect precise location, or upload to citizen science.
- Browser speech and microphone availability depend on device support and permission; visible text remains complete.
- Automated CSS checks cannot establish physical iPad Safari print pagination or touch comfort. Record real-hardware results whenever that hardware is available.
